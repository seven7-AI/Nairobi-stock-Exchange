# Database layer — `app/web/db/`

## Start here, every time

```bash
codegraph explore "UUIDMixin TimestampMixin base.py get_async_session"
codegraph explore "StockAnalysisStock external include_object env.py"
```

The second query matters most: it shows the read-only external model and the Alembic
exclusion hook. Misunderstanding that pair is how someone accidentally generates a
migration against a table this repo does not own.

## Rules

- SQLAlchemy 2.0 declarative, **async** via asyncpg. `Mapped[...]` / `mapped_column()`
  typing on every column — no legacy `Column()` style.
- Every owned model inherits `UUIDMixin` (uuid4 PK) and `TimestampMixin` (server-side UTC
  `created_at` / `updated_at`) from `models/base/`.
- One file per table under `models/`. Filename is the singular table name.
- Sessions come from `Depends(get_async_session)`. The sync engine exists for **Alembic
  and Celery only** — never import it into a request path.
- `models/services/` (DB service layer) holds queries and persistence only. **No business
  rules.** If a function decides *what a number means*, it belongs in
  `app/web/services/`, not here.

## The table we do not own

`stockanalysis_stocks` is written by an external scraper outside this repo.

- Mapped read-only in `models/external/stockanalysis_stock.py`.
- Carries `{"info": {"skip_autogenerate": True}}` and is filtered by the `include_object`
  hook in `app/alembic/env.py`.
- **Never** write to it, and never accept an autogenerated migration that touches it.
  `uv run alembic revision --autogenerate -m probe` must produce an empty migration on a
  clean tree — that is the regression test for the exclusion hook.

## Migrations

```bash
uv run alembic revision --autogenerate -m "add watchlist_items"
uv run alembic upgrade head
uv run alembic downgrade -1
```
